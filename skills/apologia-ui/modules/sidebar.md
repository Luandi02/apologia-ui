# 侧边栏 Sidebar

## 1. 意图归属

**侧边栏只在服务「并列对象之间来回切换」时才该存在。**

| 意图 | 侧边栏承担的职责 |
|---|---|
| 续接 | 保留用户正在处理的对象，随时可回去 |
| 寻的 | 提供对象间的直接跳转 |

**判据：如果用户的任务不是「在多个并列对象之间来回跳」，那么侧边栏是多余的，改用顶部导航。** 强行加的侧边栏会永久占用横向空间，压缩主内容的权重。

服务「核验」意图时，侧边栏不得承载主操作——核验场景下动作必须降级。

## 2. 形态必然性

### 推导一：侧边栏是并行任务的驻留点

- **意图**（续接）：用户同时处理 3 个工单时，切换成本必须接近 0。
- **推导**：没有常驻轨道 → 用户必须回首页再进入另一个对象，两次操作换一次切换，并行关系被反复切断。
- **结论**：侧边栏常驻，可收起但不消失。

### 推导二：只允许两层

- **意图**：切换必须是一次点击。
- **推导**：第三层会把「一次点击切换」变成「展开 → 再点」，切换成本翻倍，侧边栏失去存在理由。
- **结论**：组 → 项两层为上限，第三层改用页面内导航。

### 推导三：当前项双重高亮

- **意图**：用户随时知道自己在哪一个并行对象里。
- **推导**：仅改文字颜色时，视觉差异弱，在长列表中需要逐项扫读才能确认位置。
- **结论**：背景块 + 字重双重标记。

### 推导四：高频与主意图项置顶

- **意图**：到达距离最短。
- **推导**：按字母序或按创建时间排序，是系统归档逻辑，与用户的使用惯性无关，把检索成本转嫁给了用户。
- **结论**：主意图项置顶或单独成组。

### 推导五：底部固定锚点

- **意图**（回哪去）：用户在任何滚动位置都需要一条离开的路。
- **推导**：列表超过一屏时，底部的返回入口随滚动消失，用户在列表底部无路可退。
- **结论**：底部固定区包含至少一个返回/首页入口，不随滚动消失。

## 3. 反证

| 拿掉 / 换掉什么 | 因果在哪一环断裂 |
|---|---|
| 拿掉侧边栏（并行场景） | 并行关系断裂，用户每次切换都要回首页重新进入，用两次操作换一次切换 |
| 增加第三层 | 切换成本从一次点击变成两次，侧边栏失去存在理由 |
| 高亮只改文字颜色 | 长列表中需要逐项扫读才能确认位置，定位成本随列表长度线性增长 |
| 底部返回随滚动消失 | 用户在列表底部失去出路，必须手动滚回顶部 |
| 收起态无 tooltip | 触屏无 hover 补偿，图标语义不可自明，用户必须猜测 |

## 4. 切片存档

| 项 | 值 | 生效条件 |
|---|---|---|
| 展开宽度 | 200–280px | 桌面端 |
| 收起宽度 | 48–64px | 桌面端 |
| 层数上限 | 2（组 → 项） | 恒定 |
| 高亮方式 | 背景块 + 字重 | 恒定 |
| 图标与文字间距 | ≥ 8px | 恒定 |
| 项间垂直间距 | ≥ 4px | 恒定 |
| 底部固定区 | ≥ 1 个返回入口 | 列表超一屏时 |
| 禁用内容 | 危险操作不得置于侧边栏 | 恒定 |

> 以上是推导结论，不是法律。当意图判读改变时，需重新走第 2 段。
